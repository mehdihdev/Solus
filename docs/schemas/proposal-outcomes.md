# `proposal_outcomes` (SOLUSDEV-321 P8)

One row per decision on a SOL proposal, written by `services/outcomes.py:record_outcome` from the
router that saw the decision: `routers/sol_confirmations.py` for a card,
`routers/sol.py:_record_build_outcome` for an owned routine Build ran by itself. Read through
`GET /api/v1/projects/{project_id}/outcomes` (`docs/api/API.md` §2.9). Identifiers and digests
only: never the call's arguments, a preview row or a credential.

**Decisions.** A card's status before and after one decide request: PENDING → APPROVED is
`accepted` (the tool ran, whether or not it succeeded), → REJECTED `rejected`, → EXPIRED `expired`,
→ STALE `stale`. The gate marks a card STALE in three cases: what it would do diverged from what was
shown; its live preview was refused (a provider quota block, a refused command plan, or an argument
redaction would hide); or a tool that requires a complete preview could not produce one. Nothing
was applied in any of them. A card already settled (a repeat click) or
still pending (its tool is gone) writes no row; the status is read under the row lock the decision
takes, so two concurrent clicks write one row.

**`proposal_digest`.** For a code command (a tool in `agent/command_gate.PLAN_PREVIEW_TOOLS`), the
plan fingerprint its card showed, as 64 hex digits; a `plan fingerprint` row on any other card is
ignored. Otherwise sha256 over the call's arguments after error filing's redaction
(`agent/errors_filing._redact_args`, then `agent/tools/untrusted.redact_value` with no display path
exempted), as canonical JSON (sorted keys, no whitespace). It is lossy by design: it cannot be
re-derived from the stored transcript (whose redaction keeps call-bound display paths), and two
proposals that differ only in an argument whose name contains `key` (`key`, `hotkey`) or only in an
entropic value (a 40-hex commit sha) share a digest. An auto-run has no card, so it is always the
redacted-arguments digest, even for a code command. The digest is unkeyed until a dedicated
`SOLUS_DIGEST_KEY` makes it HMAC-SHA256; until then it is shown only to the decider.

**Indexes.** `ix_proposal_outcomes_project_created (project_id, created_at)` serves the route;
`ix_proposal_outcomes_user_id` and `ix_proposal_outcomes_conversation_turn_id` serve the
foreign-key actions of an account or conversation delete. The same migration builds
`ix_credit_ledger_user_created (user_id, created_at)` concurrently for
`GET /projects/{id}/usage/turns`, which reads one person's usage rows newest first.

**Consent.** Each row emits the consent-gated `sol.proposal_outcome` event (`{outcome_id, tool,
decision, proposal_digest}`). The row itself is product data and is written whether or not the
person consented to data collection; a training consumer reads the consented events, not this
table.
