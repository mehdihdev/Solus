**Status:** FINALIZED v1.0 (2026-06-11) — ready for phased implementation. Becomes fully
authoritative per CLAUDE.md §3 when the SOLUSDEV-2 MR merges. Implementation builds routes
exactly as planned here — paths, methods, request/response shapes. Routes and sections marked
**[DEFERRED]** are explicitly out of scope until their blocking human decision lands (§7.2);
do not implement them. A needed route missing from this plan is proposed in the MR description
and approved before building (CLAUDE.md §3). Implementation order is defined in §8.

**Governing context consulted:** CLAUDE.md (root), DECISIONS.md ADR-001…ADR-022,
`packages/contracts/README.md`, `.claude/skills/api-design`. `docs/architecture/` and
`docs/wireflows/` are currently empty; the working decisions this plan locks in their absence
are recorded in §7.1 and must be reconciled if those documents later contradict them
(higher authority wins).

This document covers four surfaces:

1. **REST API** — the FastAPI core backend (`packages/api`, planned), `/api/v1/*`
2. **Realtime** — WebSocket + SSE endpoints, `/ws/v1/*`
3. **MCP server** — Solus exposed as an MCP server for users' coding agents, `/mcp/v1`
4. **Frontend routes** — the Electron renderer route map (`apps/desktop`)

## 1. Global Conventions

### 1.1 Base URL & versioning

- All REST routes live under `/api/v1/`. URL-path versioning (skill recommendation); no v2 until a breaking change forces it.
- WebSockets under `/ws/v1/`, MCP under `/mcp/v1`.
- Infrastructure endpoints (`/healthz`, `/readyz`, `/health`) are unversioned and unauthenticated.

### 1.2 Authentication (ADR-009)

- Clients authenticate with a **Supabase Auth JWT** in `Authorization: Bearer <jwt>`. The backend validates the JWT; Solus does not run its own login/signup/password endpoints — signup, magic links, password auth, and GitHub OAuth all happen against Supabase from the client.
- Team scoping is enforced by **centralized middleware** (CLAUDE.md §7) on every protected route. No per-endpoint ad-hoc auth.
- WebSocket connections authenticate at connect time (token in first message or query param) and are scoped to one team's project.
- Inbound webhooks (GitHub/GitLab/Onshape) authenticate via provider signature verification, not bearer tokens.

### 1.3 Tenancy model

```
User ──member of──▶ Team ──owns──▶ Project ──contains──▶ Graph (entities, relations), Sources, Bench, …
```

- **Every individual user gets a personal team created at first login.** This is what makes the individual→team upgrade flow (ADR-015) a billing transition rather than a data migration.
- **Locked at finalization (§7.1):** one graph per project, multiple projects per team. The graph, sources, bench, warnings, and all other feature-area resources hang off the project.
- Collection routes are nested under their owner (`/teams/{team_id}/projects`, `/projects/{project_id}/entities`). Middleware resolves `project_id → team_id` and enforces membership on every request. Cross-tenant isolation tests are mandatory per endpoint (CLAUDE.md §6/§7).

### 1.4 Request/response conventions

- JSON, `snake_case` field names (Pydantic v2 backend; the typed TS client maps as-is).
- IDs are UUIDs (UUIDv7 preferred for index locality), opaque to clients.
- Success envelope: `{ "data": …, "meta": …?, "links": …? }`. Error envelope:
  `{ "error": { "code": "...", "message": "...", "details": [...] } }` with semantic HTTP status codes (400/401/403/404/409/422/429).
- **Pagination:** cursor-based by default (`?cursor=&limit=`, `meta.has_next`, `meta.next_cursor`). Offset allowed only on small admin-ish lists.
- **Filtering/sorting:** `?field=value`, bracket comparators (`created_at[after]=`), `?sort=-created_at`, `?q=` for search.
- **Long-running work never runs in the request path** (ADR-005). Any heavy operation returns `202 Accepted` with a Job resource (`{ "data": { "job_id": …, "status": "queued" } }`) and a `Location: /api/v1/jobs/{job_id}` header. Progress is polled via Jobs; status changes are pushed as a `job.updated` hint on the project event stream (§3, ADR-037).
- **Idempotency:** mutating POSTs accept an optional `Idempotency-Key` header; required on billing and deployment endpoints, and on extension publishing (`POST /extensions/publish`, §2.17 — SOLUSDEV-235).
- **Rate limiting** (CLAUDE.md §7, ADR-019): all endpoints return `X-RateLimit-Limit/Remaining/Reset`; 429 includes `Retry-After`. Model-backed endpoints additionally enforce credit budgets and return `X-Solus-Credits-Charged` and `X-Solus-Credits-Remaining` headers (ADR-018).
- **SOL mode** (ADR-016): every endpoint that produces natural-language output reads the per-user mode from settings. An optional `X-Sol-Mode: guide|expert` header overrides per-request (e.g., "explain this one to me").
- **Data events** (ADR-011): meaningful interactions emit structured events server-side automatically; the explicit ingestion endpoint (§2.13) exists for client-originated events only.

### 1.5 Metering classes (ADR-018)

| Class                 | Examples                                                                                            | Billing                                                                   |
| --------------------- | --------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| **Unmetered**         | CRUD, graph reads, pure-logic checker runs, ambient autocomplete warnings, sync                     | Included in subscription                                                  |
| **Metered (credits)** | Agent conversations, deep diagnoses, LLM warning explanations, fingerprint LLM passes, proving runs | Per-user / pooled team allowance; graceful "lite mode" degradation at cap |

**Extensions (§2.17, SOLUSDEV-235 / ADR-035):** every route on the Extensions & Store surface —
catalog, publishing, installs, storage, widget layout, team policy — is **Unmetered**; none of it
calls a model. The only metered consequence of an extension is a SOL turn the desktop host makes
on its behalf, and that is charged on the EXISTING SOL routes: the host sends
`X-Solus-Extension: <slug>`, the server accepts it only when the project has an enabled install
granting `sol.ask` (else `403 scope_denied` — refused, never ignored), records `extension_id` on
the `credit_ledger` row for attribution, and still meters the **invoking user** (ADR-018/019/024
— per-user credits, no pooling, no separate extension budget). See
[extensions.md](extensions.md) §9.

### 2.4 Graph — entities & relations (ADR-001, the core)

Connector-owned entities/relations are **read-only** through this API (the connector is the source of truth; edits happen in the source tool and arrive via sync). Manually created entities (`origin: "manual"`) are user-editable. Concurrency uses optimistic versioning: writes carry `If-Match: <version>`; a stale version returns `409` with the conflicting change summary (feature area 10's graph-informed conflict detection).

**SOLUSDEV-242:** entity creation/rename/removal currently supports only manual,
source-null `physical_robot` roots; other mutation kinds remain deferred. The
exact payloads, seven owned categories, preserved-part deletion, paginated
`orphaned_from_robot` read and `graph_updated_at` validator are specified in
[`workspace.md`](workspace.md#phase-4--physical-robot-instances). Manual mutations
publish committed `graph.changed` hints with null `source_id` and `sync_id`.

Behaviour that API consumers and the webhook must honour:

- **Effective limits.** Enforcement and `GET/PATCH /users/me/subscription` read `effective_limits(subscription)` only: the plan-derived `limits` (webhook-maintained, or the comp plan's defaults while a comp is active) merged **per key** under a staff `limits_override` (explicit `null` = unlimited, absent key falls through to the plan default). Enforcement never reads plan names (ADR-023).
- **Webhook convergence.** Stripe is the source of truth for Stripe-backed subscriptions: staff plan changes, comps and cancels are applied in Stripe and converge locally through `customer.subscription.*` events (`stripe_event_at` last-write-wins; replays deduplicated by event id). Webhooks never write or clear `limits_override`. An event is worded as staff-initiated only when `data.previous_attributes.metadata` shows `solus_admin_action_id` changed in that event; the signature remains the only trust anchor. A new Stripe subscription link (an incoming non-terminal subscription id that differs from the stored one, e.g. a resubscribe after cancellation) clears a local (non-Stripe) comp; replays of the same id and terminal events never do. `PATCH /users/me/subscription` accepts only the self-serve plans (`basic`, `pro`); `enterprise` is rejected with 422 `validation_error`.
- **Comps.** Stripe-backed comps use a deterministic 100%-off coupon (`solus-comp-once` / `solus-comp-repeating-<N>` / `solus-comp-forever`) plus a Subscription Schedule that reverts to the previous price when the coupon ends. Non-Stripe comps are stored on the subscription (`comp_plan`, `comp_expires_at`; `once` = 1 month, `repeating N` = N months, 1-36, `forever` = no expiry), ignored at read time once expired, and materialised by an ARQ sweep that also notifies the user. A local comp to a paid plan grants that plan's starting credits through the existing idempotent plan-grant key.
- **`PATCH /users/me/subscription`.** Allowed only while the subscription is `trialing` with no Stripe subscription; otherwise `409 subscription_change_not_allowed`. It never resets `expires_at` (no trial restarts).
- **Account deletion (`DELETE /users/me`).** Deleting an account cancels its Stripe subscription immediately, creating a final invoice and applying no proration (business policy). The cancellation is a durable `stripe_cancel_requests` row written in the deletion transaction, attempted best-effort after commit and retried by a worker cron and at API startup; deletion is never blocked by Stripe. The Stripe Customer is not deleted. The row is retained as a tombstone: a subscription created later for that customer (checkout in flight at deletion) is canceled by the webhook path. Webhooks for already-deleted users are safe no-ops. The extracted deletion service also accepts a validated `ownership_transfers: {team_id: new_owner_user_id}` for staff callers (SOLUSDEV-314); the self-service route never exposes it.

## 3. Realtime — WebSocket & SSE

WebSocket implementations live behind the isolated telemetry service boundary (ADR-005) so the Rust rewrite (ADR-004) swaps the implementation, not the interface. All connections authenticate at connect time and are scoped to one team's project (§7). Device-originated telemetry is parsed defensively: bounded message sizes, malformed packets dropped and logged, never crash the service.

| Protocol | Path                                            | Direction     | Description                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| -------- | ----------------------------------------------- | ------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| SSE      | `GET /api/v1/projects/{project_id}/events`      | server→client | Project event channel (SOLUSDEV-167). Carries `graph.changed` — an invalidation **hint** (`{type, project_id, source_id, sync_id, counts, at}`, ~200 bytes), never a delta: the host refetches its one focused key, so N mounted lenses stay one request (`widget-contract.md` §"never fetch your own scope"). **SSE, not WS, and the reason is auth**: the only existing WS auth in this repo reads an `Authorization` header, which works solely because the companion is a Python client — no browser `WebSocket` can set a header, and the renderer is Chromium. **Locked at finalization (§7.1):** SSE for agent response streaming, WS for telemetry — Electron's Chromium renderer supports both natively, and the one-shot nature of agent responses fits SSE.

**SOLUSDEV-262 live-display implementation:** the documented
`/ws/v1/bench/sessions/{session_id}` initially implements read-only telemetry.
Within five seconds the browser sends one bounded JSON authentication frame
`{type:"authenticate", token:<normal bearer token>, project_id:<UUID>}`.
Credentials never appear in URLs or logs. The server uses the centralized token,
user and project authorization checks and verifies that the session belongs to
that project before emitting any data. Token expiry is checked each streaming
iteration; membership and graph visibility are rechecked at most five seconds
apart and when observed session mappings change. Expiration, failed reauthorization,
session end or disconnect terminates delivery. Control/motion messages are not implemented.

Server frames are `{type:"telemetry", project_id, session_id,
devices:[<DeviceRecentOut>...]}` using the existing device-recent signal shape,
actual sample timestamps and confirmed signal roles. Changed snapshots are
coalesced at at most 10 Hz, with bounded history (128 samples per signal inside
eight seconds), session-scoped device selection and bounded subscriber resources.
Streaming reads the existing telemetry buffer without opening hardware or polling
the database on each frame. Slow consumers must not build an unbounded backlog or
block acquisition. When no snapshot changes, a liveness frame
`{type:"heartbeat", project_id, session_id}` is sent every five seconds; it never
refreshes sample timestamps. The renderer shares a session stream across signals, widgets
and scene, clearing data across account/project changes. REST recent-values reads
remain a fallback; fallback cadence must not be described as realtime. A gap marks
established channels stale instead of deleting their cards or inventing samples.

**Amended — SOLUSDEV-167:** the **project event channel is SSE**, not WS. The original choice assumed the bridge's WS auth could be reused; it cannot — that pattern reads an `Authorization` header, which is available only because the companion is a Python client. A browser `WebSocket` cannot set headers, so WS here would mean inventing a second credential path (subprotocol- or query-carried) plus reconnect logic in the client, to buy a bidirectional channel nothing needs. SSE runs under the ordinary `ProjectCtx` dependency and reuses the shipped client parser. Consequently there is **no client `subscribe` frame and no topic set** — connecting to a project's stream IS the subscription, and `graph.changed` was the only event type produced until SOLUSDEV-250 added `hardware.devices_changed` (below). `warnings` and `jobs` become additional event types on the same stream when their producers exist; `presence` stays **[DEFERRED — §7.2.4]** on its own schema. The SSE `event:` name is the frame's `type` (a lowercase dotted token); a frame without a valid one is sent as `graph.changed`.

**Amended — SOLUSDEV-250 (hot-detect):** the same stream carries `hardware.devices_changed` — `{type, project_id, devices: [<GET /hardware/detected row>…], at}`. Unlike `graph.changed` it is a **full current list**, not a hint: the data is small, ephemeral and machine-local (there is no server state to refetch), and absence from the list is the removal. Produced only by the **local** API process (`hardware/device_watch.py`): it diffs `detect_devices()` at ~1 Hz (no port opened, nothing enumerated while the process has no subscriber) and emits only when the list changes. Delivery is **local-only** — `LiveHub.publish_local`, never Redis — so one machine's devices never appear in another machine's session. Informational: it does not touch the graph, and nothing auto-accepts from it. WS remains the telemetry transport (`/ws/v1/bench/sessions/{session_id}`), where the client genuinely sends control input.

**Amended — SOLUSDEV-312 (ADR-037, live channels):**

- **Three channel kinds** — `project:{id}`, `team:{id}`, `user:{id}` — on Redis pub/sub `solus:live:{kind}:{id}` (the relay also accepts the legacy `solus:graph:{project_id}`). Routing is structural: the channel is derived server-side from the committed row's scope.
- **Publish after commit.** Frames are derived from ORM changes at flush, queued on the session and published in `after_commit`; rollback publishes nothing; a publish failure never fails the request. Derived hints: activity rows → `team.activity`; notification rows → `notification.created`; team/membership/project-share/invite/project/source/workspace-layout/job changes → the matching hint (table in `docs/contracts/live-events.md`). Progress-only job updates and cursor/config-only source updates publish nothing.
- **Project stream additions:** `layout.changed` (`version`), `sources.changed`, `project.updated`, `job.updated`, `access.revoked`. This supersedes the "`warnings` and `jobs` become additional event types" note above for jobs; `warnings` remain future.
- **Re-verification.** Both streams re-verify access (token re-decoded, membership/share re-checked in a short-lived session) at most every 30 s and immediately on a `membership.changed`/`access.revoked` for the caller. When access is gone the server sends `access.revoked` and ends the response. A removed member therefore stops receiving hints within 30 s at worst.
- **No replay.** Reconnecting clients revalidate everything on `ready`.
- **Limits.** At most 8 concurrent live streams per user per API process (`429 rate_limited`). `/health` (alias of `/readyz`, ADR-037 §4) reports `checks.live_fanout = redis | local_only`; without Redis, delivery is process-local and multi-instance deploys would split subscribers.
- `presence` remains **[DEFERRED — §7.2.4]**.

## 6. Cross-Cutting Security Checklist (binds every endpoint above)

Restating CLAUDE.md §7 obligations as they apply to this surface — every implementing MR must satisfy:

- [ ] Centralized authN/authZ middleware; team-scoped queries; cross-tenant isolation test per endpoint
- [ ] Pydantic validation on every input; unknown fields rejected on sensitive endpoints
- [ ] Connector/webhook/telemetry/error payloads treated as untrusted (bounded, parsed defensively)
- [ ] Ingested content reaching any prompt is wrapped as data — never instructions (agent, explanations, overlay)
- [ ] Model-proposed tool calls validated against schema + authz before execution; destructive actions require explicit approval (§2.9 actions)
- [ ] Rate limits on everything; credit budgets + loop guards on all metered routes (ADR-019)

- [ ] No secrets in model context, ever
- [ ] Structured event emitted for every meaningful interaction (ADR-011)

### SOLUSDEV-242 Phase 3 — Workspace service selection amendment

This amendment tightens I1 reads and source reuse without adding a new route.

- Account `/users/me/connections/{connection_id}/documents` and project source
  `/projects/{project_id}/sources/{source_id}/selectable` accept `cache_only=false`.
  `cache_only=true` returns the existing `{data,meta:{cached,fetched_at}}` on a hit,
  or **409 `listing_not_cached`** on a missing, expired, malformed or unavailable cache.
  It must not resolve credentials or invoke any provider callback. Combining
  `cache_only=true` with `refresh=true` is **422 `validation_error`**.
  Explicit `refresh=true` remains the existing cooldown-limited I1 listing operation.
- The Workspace Add surface retains both results and cache-miss states by authenticated
  identity/account. Opening/reopening a loaded dropdown or panel issues zero new listing
  requests; “Load documents”/“Refresh documents” is the deliberate refresh action.
- `POST /projects/{project_id}/sources` with `connection_id` reuses only a source for that
  account and selection (a Git repository is its own source; Onshape tracks multiple
  documents per account/source). Exact reuse preserves status/errors and does not consume
  another integration slot. A different account never silently rebinds a source. A legacy
  unbound source may be adopted only when its known provider identity matches the grant.
- Concurrent document additions serialize source selection changes. Duplicate selection
  remains the existing 200 `unchanged` with null job ID; a newly tracked document is 202
  with one accepted job. First selection ingests once. Existing selection/node navigation
  never enqueues another job from Workspace.
- Onshape graph output includes one `cad_document` root per selected document, with
  `properties.document_id`, source/project identity and `contains` edges to assembly roots.
  Existing part keys, IDs and `part_of` edges remain. Names use I1's cached metadata or the
  actual document ID; missing listing data is never a reason to list the provider implicitly.
  Existing graphs receive wrapper roots through a local backfill, without provider ingestion.

### SOLUSDEV-260 entity search clarification

The existing project-scoped entities GET `q` matches names and stored connector
code paths (`external_ref`/`properties.path` for code entries), with literal wildcard
escaping and existing source/type/deleted/tenant filters. No route or response shape
changes. A selected mention anchors graph metadata; source-file contents require
the existing authorized tool path.

### Local-tool platform availability (SOLUSDEV-261)

`GET /api/v1/integrations/local-tools` adds `supported_platforms`: null when no restriction is declared, otherwise an array of `linux`, `darwin`, and/or `win32`. An empty array means invalid platform metadata and disables connection. `display_name` and restrictions come from the Solus-owned `integrations/mcp/<server>/platform.json`, never from the API host OS or companion claims. Metadata is bounded to 4 KiB, validates unknown fields and platform names, and refuses paths outside the integrations root. Missing metadata preserves existing unrestricted tools. Authentication and catalog membership remain unchanged.

### Development credit exception (SOLUSDEV-261)

ADR-024 permits an explicit development-only account allowlist. `GET /api/v1/users/me/credits` returns `{user_id, balance, unlimited}`; `GET /api/v1/users/me/usage` adds the same boolean `unlimited`. Only the authenticated current user is evaluated. `balance` and `used` remain real ledger values. `unlimited` is true only when server configuration names that UUID and `app_env` is exactly `dev`. No client request can change this entitlement. Billing and the usage meter display “Unlimited (development)” when true. All production responses report false.

### Build action policy (SOLUSDEV-261)

The existing `action_mode: "do"` wire value represents Build. Its centrally
classified routine tool operations execute after complete fresh validation without
a pending human card; execution provenance is Build authorization. Destructive or
unclassified tools still use the existing confirmation endpoints. Guide cannot
mutate. This adds no endpoint, client risk flag, or privilege-elevation parameter.

### SOLUSDEV-261 Onshape webhook amendment

The existing provider webhook route may parse a bounded JSON body after source-token
authentication to extract provider event identity and document/workspace hints for
deduplication. This supersedes the earlier instruction to discard the entire body.
No payload field grants tenant/project/source authority. Invalid/foreign hints cannot
expand the source's tracked document selection. Authenticated hints are durably
coalesced in internal source metadata, including arrivals during sync, and handed to
ARQ. Rate limiting retains a pending dirty indication instead of losing freshness.
Lifecycle and generation semantics follow `docs/architecture/change-signal-spine.md`.
No new public route is introduced by this amendment.

### Onshape verified grant and revision acquisition continuation — SOLUSDEV-261

No new route or public request field is introduced. Existing OAuth completion binds
private application identity only after successful grant verification and mirrors
it through the existing account-to-source binding. REST metering and quota health
use this verified application plus account identity. Changing configured client
credentials alone does not reassign a grant or clear its counters. Legacy unbound
grants retain their previous quota scope; old application records and exhaustion
latches are retained. Secret rotation within the same application preserves its
ledger. Public OAuth REST exemption and any observed hosted-service allocation
remain separate policies; no annual MCP entitlement is inferred.

Existing source-sync jobs now acquire immutable element/metadata revisions and
verify workspace STEP translations before publishing `revision-v2-*` cache entries.
The `cad-geometry-v3` cursor repairs existing tracked sources once after successful
reingestion. All six feature-spec callers use immutable `/m/` specs selected from a
fresh feature tree, with account/revision/collection isolation. Full details and
cold/warm request costs are in `onshape-development.md`. Existing job identity,
project authorization, complete-snapshot and no-automatic-write-replay rules remain
unchanged.

### SOLUSDEV-261: bounded multi-step Build turns

The existing SOL turn route selects server-owned loop limits from its validated
action mode. Guide retains 5 model rounds, 8 tool calls and 120 seconds. Build
permits at most 16 model rounds, 24 tool calls and 300 seconds, reserving the last
model round for tool-free synthesis. Short answers still terminate immediately.
These are hard ceilings, not requests to consume the allowance. Every model round
retains existing identity, rate, spend and credit gates; every integration request
retains provider quota enforcement. The transport independently enforces tool
count and wall-clock limits even for a runaway runner. No client-supplied numeric
budget, tool output, account tier or development credit override can increase
these bounds. Stream teardown has a separately bounded cleanup grace of at most
5 seconds, never permission for additional model or tool dispatch. Cancellation
closes the active stream and persists completed work;
uncertain writes are not replayed. Action permissions and approval gates are
unchanged. The change supports discovery, inspection and verified execution in
one Build request rather than stopping before geometry can be inspected.

### SOLUSDEV-261: deferred graph reconciliation within Build turns

For an admitted native Onshape write in a SOL turn, durable dirty bookkeeping
and a bounded server-owned source/turn hold precede invocation. Successful tool
results may return `graph_sync.status=deferred` until turn cleanup releases its
hold and enqueues one normal sync per affected source. Uncertain writes retain
their error without replay; conservative dirty marking permits later read-only
reconciliation. Scope, live account grants, tool policy and provider quotas remain
authoritative. Confirmation decisions outside a running turn remain immediate.
Expiry and independent owner holds follow `change-signal-spine.md`; the existing
turn cleanup remains bounded, and failed cleanup cannot erase durable recovery.
