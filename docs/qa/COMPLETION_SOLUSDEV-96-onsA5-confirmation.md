# Completion Report — SOLUS-ONS-A5: the destructive-action confirmation round-trip

**Status:** built, verified, on `SOLUSDEV-60/ons-a5-confirmation`. Ends at the per-ticket gate.

## Why this came before A3

Phase 0 found that `confirmation_refusal` was **a hard refusal, not a gate**: its own docstring said
*"that confirmation flow does not exist yet, so the gate refuses outright."* Any tool declaring
`requires_confirmation` returned `UNAUTHORIZED` 100% of the time. Building A3's write tools first
would have shipped code that could not run. This makes them runnable the moment they exist.

## The shape, and why the transport forced it

A SOL turn is a one-shot SSE stream. It cannot block for minutes waiting for a click, and holding
the request open would pin a worker. So a gated call **parks**: the turn records what it wants to
do, streams the concrete action, and ends. The user decides through a separate endpoint, and the
tool runs *there* — with the registry rebuilt under the deciding user's own scope.

## The load-bearing security property

**Arguments are server-side.** `ToolConfirmation.args` holds exactly what the user was shown and
exactly what executes. `ConfirmationDecision` is a `StrictModel` carrying `decision` and nothing
else, so a body with its own `args` is a **422, never a merge** — otherwise a user could approve
"change width" and a client could execute "change everything". Pinned by
`test_the_endpoint_never_accepts_arguments_from_the_client`, which also asserts the row is left
`PENDING`.

Supporting properties, each with a test:

| property | why it matters |
|---|---|
| **Single use** — status is set to `APPROVED` *before* dispatch | one approval is not an unlimited licence to repeat a destructive action; a crash mid-execution must not leave the row replayable. Losing an execution is recoverable; repeating one is not. |
| **Only the requesting user may decide** | a teammate never saw the proposed action |
| **Wrong project / wrong user / absent are all `NOT_FOUND`** | no existence oracle (the `get_entity` rule) |
| **30-minute TTL**, and expiry settles the row | an approval is consent to a specific edit against a specific model state, and CAD moves |
| **Tool gone at approval time is refused** | the registry is rebuilt per request; a source disconnected in between means the tool is simply gone |
| **`park` absent ⇒ falls back to the flat refusal** | a missing wire must never mean "dispatch anyway" |

## What was built

- **`models.ToolConfirmation`** + `ConfirmationStatus`, tenant-scoped by `project_id`/`team_id` FKs
  with CASCADE, plus `user_id` as the decider. Migration `07f6c043efa3` (autogenerated, formatted);
  **single head**.
- **`agent/confirmations.py`** — `request_confirmation` (park or return `None`) and
  `decide_confirmation` (approve/reject, execute on approval). Every failure path returns a
  `ToolResult`, never an exception, so W0-04's never-raises story holds through this path too.
- **`agent/runtime.gate_tool_call`** — the gate a runner now calls. `confirmation_refusal` is kept
  as the documented fail-closed fallback rather than deleted.
- **`AgentRunContext.park`** — supplied by Solus code with session/team/user already bound, so the
  reasoning layer never grows a DB dependency.
- **`AgentEventType.TOOL_CONFIRMATION`** — streamed inline right after the parked call's result,
  carrying tool, args and a readable summary. A user cannot meaningfully approve an opaque id.
- **`POST /api/v1/projects/{p}/sol/confirmations/{id}`** — MEMBER role, `ProjectCtx` scoping,
  emits a data-collection event.

## Not in this ticket, and honestly stated

- **No renderer UI.** The stream event and the endpoint exist; nothing in the desktop app renders
  an approve/reject prompt yet. So today a parked action is visible to an API client but not to a
  user in the app. This is the same boundary A2 left (no picker UI), and both want the same small
  piece of renderer work — I'd rather do them together than half-build each.
- **The summary is rendered from the tool's own `ToolDescriptor.description` plus its arguments.**
  Solus-authored, never model- or server-supplied, so it cannot be used to phrase a misleading
  prompt. Good enough to approve against; a richer per-tool renderer (A4's diff) is the next step.
- **No expiry sweeper.** Expired rows settle lazily when someone tries to decide them. A background
  sweep is worth adding when volume justifies it.
