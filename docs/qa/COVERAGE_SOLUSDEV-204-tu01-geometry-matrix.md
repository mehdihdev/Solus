## 2. Per-Tool Detail

### 2.1 Onshape

- **REST API is data-plane only** — documents/elements/parts/features; nothing describes UI controls, toolbars, or screen positions. No endpoint enumerates the built-in command set. ([api-intro](https://onshape-public.github.io/docs/api-intro/), [openapi](https://cad.onshape.com/api/openapi))
- **Featurespecs trap**: all three `featurespecs` endpoints are per-document and return the *customer's* feature specs (including their custom FeatureScript) — never ingest as a vendor command catalog. ([featureaccess](https://onshape-public.github.io/docs/api-adv/featureaccess/))
- **FeatureScript**: std library is public and version-pinned per import → built-in feature semantics enumerable from FsDoc + the public std document; vendor content, safe for the KB. Feature preconditions define dialog *logical* contents, zero pixels. ([fs docs](https://onshape-public.github.io/docs/api-adv/fs/))
- **App extensions**: location vocabulary (element tab, right panel, context-menu, toolbar actions) documents which UI insertion points exist; apps are sandboxed iframes, learn no positions. postMessage channel assessed no-geometry from overview only (full message list unverified — fetch failed). ([extensions](https://onshape-public.github.io/docs/app-dev/extensions/))
- **DOM is the only geometry channel** and legitimate for a web tool — but the modeling viewport is WebGL canvas (no DOM for parts/sketch entities), and selector stability is structurally unguaranteed: all users on the latest build every ~3 weeks, no pinning, no DOM contract. Treat selectors as date-scoped, monitored, centrally updatable — not KB facts. ([release cadence](https://www.onshape.com/en/blog/cloud-native-cad-software-automatic-updates-new-features))
- **Command/menu/shortcut logical structure**: scrapeable from the help site ([keyboard shortcuts](https://cad.onshape.com/help/Content/Home/keyboard_shortcuts_and_hotkeys.htm)); shortcuts are user-customizable, so live shortcut→command maps are per-user state. No machine-readable command manifest found. API changes tracked at the [changelog](https://onshape-public.github.io/docs/changelog/).
- **Accessibility**: no desktop app — collapses into browser a11y tree over the same DOM; ARIA quality unverified.

### 2.2 Autodesk Fusion

- **Full logical UI enumeration**: `UserInterface.commandDefinitions` lists ALL commands (id/name/tooltip/icons); `workspaces → toolbarTabs → toolbarPanels → controls` gives placement, `ToolbarControl.index` order, visibility, `isPromoted`. Vendor's own "Write user interface to a file" sample dumps the hierarchy to XML with zero coordinates — structure-only by design. ([commandDefinitions](https://help.autodesk.com/cloudhelp/ENU/Fusion-360-API/files/UserInterface_commandDefinitions.htm), [WriteUserInterfaceToFile sample](https://help.autodesk.com/cloudhelp/ENU/Fusion-360-API/files/WriteUserInterfaceToFile_Sample.htm), [ToolbarControl](https://help.autodesk.com/cloudhelp/ENU/Fusion-360-API/files/ToolbarControl.htm))
- **Geometry exceptions**: `Palette` exposes `left/top` "relative to screen space and in pixels" (get+set), width/height, docking — including native palettes via `itemById`; docked-state read behavior undocumented (probe needed). `Viewport` gives canvas px + full screen↔view↔model transform chain — anchors overlays to model geometry, says nothing about chrome. ([Palette](https://help.autodesk.com/cloudhelp/ENU/Fusion-360-API/files/Palette.htm), [Viewport](https://help.autodesk.com/cloudhelp/ENU/Fusion-360-API/files/Viewport.htm))
- **TextCommands palette**: undocumented-but-stable execution/introspection backchannel (`Commands.Start <id>`); no geometry; output format not contractual. ([TextCommandPalette](https://help.autodesk.com/cloudhelp/ENU/Fusion-360-API/files/TextCommandPalette.htm))
- **Accessibility unknown, not partial**: UI is Qt ([forum confirmation](https://forums.autodesk.com/t5/fusion-api-and-scripts-forum/what-ui-framework-is-the-fusion-360-user-interface-built-on/td-p/7409179)), Qt bridges UIA/NSAccessibility in principle ([Qt docs](https://doc.qt.io/qt-6/accessible.html)) — but the toolbar is custom-rendered and no vendor doc claims coverage; untested on a real install (and untestable on this host).
- **Customer-content traps**: `commandDefinitions`/panels/palettes include third-party add-in registrations; window titles and browser palette carry customer document names. KB ingester must filter to known-native ids or tag provenance.
- **Version scoping**: no annual versions, one rolling doc set, no archives; scope facts by capture date + build number. 2019 tabbed-toolbar overhaul is precedent that UI-structure entries carry the churn risk.

### 2.3 SolidWorks

- **Best-documented geometry of the six**, three tiers: frame rects (`FrameLeft/Top/Width/Height`, pixels, get+set, valid only at `swWindowNormal`); per-model-view rects (`IModelView::Frame*`); and **per-button** `ISldWorks::GetButtonPosition(commandID)` returning the button center (SW2010+) — coordinate space and CommandManager-vs-classic-toolbar coverage undocumented, needs empirical probe. ([GetButtonPosition](https://help.solidworks.com/2024/english/api/sldworksapi/SolidWorks.Interop.sldworks~SolidWorks.Interop.sldworks.ISldWorks~GetButtonPosition.html), [FrameLeft](https://help.solidworks.com/2024/english/api/sldworksapi/SolidWorks.Interop.sldworks~SolidWorks.Interop.sldworks.ISldWorks~FrameLeft.html))
- **Win32 handle bridge**: COM deliberately hands out `IFrame::GetHWnd/GetMenu`, `IModelWindow::HWnd` → `GetWindowRect`/`GetMenuItemRect`/`EnumChildWindows` give full pixel geometry; PropertyManager pages are real Win32 children ('Dve sheet' container + stock control classes). CodeStack caveats: raw IDs not permanent across releases, locale-dependent text. ([CodeStack PMP](https://www.codestack.net/solidworks-api/application/frame/property-manager-page-windows-api/), [capture-commands](https://www.codestack.net/solidworks-api/application/frame/capture-commands/))
- **Command enumeration**: `swCommands_e` publishes 3000+ IDs per release year, harvestable without an install ([swCommands_e](https://help.solidworks.com/2024/english/api/swcommands/SolidWorks.Interop.swcommands~SolidWorks.Interop.swcommands.swCommands_e.html)); runtime menu tree via `IFrame::GetSubMenus` (SW2003+); native CommandManager tab **names** via `IModelDocExtension::GetCommandTabs` (SW2014+) — but no documented API lists the buttons inside a *native* tab (button-level enumeration is add-in-tabs only via `ICommandTabBox::GetCommands`). Live events (`CommandOpenPreNotify`) stream executed IDs. ([GetCommandTabs](https://help.solidworks.com/2024/english/api/sldworksapi/SolidWorks.Interop.sldworks~SolidWorks.Interop.sldworks.IModelDocExtension~GetCommandTabs.html), [RunCommand](https://help.solidworks.com/2024/english/api/sldworksapi/SolidWorks.Interop.sldworks~SolidWorks.Interop.sldworks.ISldWorks~RunCommand.html), [CADSharp](https://www.cadsharp.com/blog/runcommand-the-swiss-army-knife-of-the-solidworks-api/))
- **UIA: strictly unknown** — no vendor a11y docs, no third-party reports either way; expectation that stock Win32 surfaces appear and custom-drawn CommandManager/FeatureManager/Task Pane may not is labeled inference ([MS custom-UI caveat](https://learn.microsoft.com/en-us/troubleshoot/power-platform/power-automate/desktop-flows/ui-automation/element-picker-cant-see-elements)). No UIA claims in the KB before an Inspect.exe/FlaUI probe (impossible on this host).
- **Version scoping is exemplary**: per-year doc URLs (2010–2026), each member page carries "Availability: SOLIDWORKS <year> FCS" — every KB fact gets an exact version floor; year-over-year swCommands_e diffs give per-release deltas. Not stable: enum numeric values (undocumented), WM_COMMAND/control IDs, enum-name↔UI-label mapping. Note: help site needs a browser UA (plain fetch 403s; content in `__NEXT_DATA__` JSON).
- **Customer-content trap**: every runtime enumeration reflects the user's customized UI + add-in injections + document titles. Harvest from a clean vanilla install only.

### 2.4 AutoCAD

- **CUIx is the crown jewel for logical structure**: a ZIP-of-XML parseable **without running AutoCAD** — workspaces, ribbon tabs/panels/rows/items, toolbars, menus, QAT, shortcut keys, and the macro each element fires. Schema unpublished (community-derived, stable-in-practice since 2010, vendor-unwarranted). Supported in-process equivalent: `CustomizationSection` managed API. ([CUI managed API](https://help.autodesk.com/cloudhelp/2017/ENU/AutoCAD-NET/files/GUID-01548FB4-7DE1-4025-B4C6-5E33D3530E15.htm), [cuix format](https://www.cadforum.cz/en/how-to-convert-cui-file-to-mnu-or-cuix-to-cui-tip8482))
- **Ribbon runtime** (`Autodesk.Windows`/AdWindows.dll): live logical ribbon tree incl. third-party tabs; **no documented screen-rect property found** on RibbonTab/Panel/Item (absence inferred from the documented property set, not an exhaustive reference). WPF visual-tree walk + `PointToScreen` is an undocumented, unverified derivation; AdWindows is internal beyond a few classes. Documented geometry crumbs: `Editor.PointToScreen` (drawing→screen, canvas overlay anchor) and an unverified `StatusBarItem.PointToScreen` index entry. ([Editor.PointToScreen](https://help.autodesk.com/view/OARX/2018/ENU/?guid=OREFNET-Autodesk_AutoCAD_EditorInput_Editor_PointToScreen_Point3d_int))
- **COM geometry is narrow and legacy**: `AcadToolbar` Top/Left/Width/Height + window rects; ribbon absent from COM (asserted from doc silence); legacy toolbars hidden by default in modern workspaces, so this rarely covers what an overlay needs. ([ActiveX Toolbar](https://help.autodesk.com/cloudhelp/2018/ENU/AutoCAD-ActiveX-Reference/files/GUID-46BA804C-6A7F-482E-BF42-BCE9C2F2DAA2.htm))
- **Command enumeration**: union of CUIx + per-release Command Reference is the practical full set; `AcEdCommandIterator` gives runtime ground truth but misses demand-loaded modules ([ADN blog](https://blog.autodesk.io/how-to-get-list-of-autocad-commands/)).
- **UIA plausible but unverified**: WPF chrome should expose BoundingRectangles; no vendor UIA docs, no AutoCAD-specific walkthrough found; canvas likely opaque. Only plausible *external* geometry channel; reliability unknown.
- **Version scoping**: hard binary gate — in-process probes must be rebuilt per engine generation (2021–24; 2025–26 .NET 8; 2027 new engine .NET 10) ([2027 SDK](https://blog.autodesk.io/autocad-2027-sdk-what-every-plugin-developer-needs-to-know/), [engine post](https://aps.autodesk.com/blog/end-autocad-2021-engine-new-autocad-2027-engine-released)). Tag CUIx-derived entries with extraction release.
- **Customer-content trap**: partial/enterprise CUIx files carry customer macros, tool names, network paths; live ribbon includes plugin tabs. Whitelist to shipped `acad.cuix` / menugroup ACAD only.

### 2.5 KiCad

- **IPC API (9+)**: design-model only — board objects, commits, `run_action(name)` (explicitly UNSTABLE) for logical command dispatch; **no messages for menus, toolbars, windows, or screen positions** (conclusion rests on kipy docs + dev-docs + community guide; full .proto tree not exhaustively audited). Off by default; PCB-only in 9/10; schematic+headless in 11. ([IPC dev-docs](https://dev-docs.kicad.org/en/apis-and-binding/ipc-api/), [kipy](https://docs.kicad.org/kicad-python-main/))
- **SWIG + wx tree walk is the only real geometry channel and it is on a death clock**: in-process wxPython gives `GetScreenPosition/GetScreenRect` for chrome (toolbars, menus, panels, dialogs) — but GAL/OpenGL canvas items are not widgets, world→screen transform exposure unverified, and SWIG is deprecated at 9.0 with removal planned for 11.0. Primary source for the technique (kicad.mmccoo.com) is offline; confirmed only via snippet + wx fundamentals. ([pcbnew bindings](https://dev-docs.kicad.org/en/apis-and-binding/pcbnew/index.html), [mmccoo](https://kicad.mmccoo.com/2017/03/05/adding-your-own-command-buttons-to-the-pcbnew-gui/))
- **Command enumeration is the strength** — four independent channels: versioned manuals ([9.0](https://docs.kicad.org/9.0/en/kicad/kicad.html), [8.0 eeschema](https://docs.kicad.org/8.0/en/eeschema/eeschema.html)); hotkey editor / `user.hotkeys` action namespace + GPL source TOOL_ACTION definitions at a git tag; `kicad-cli --help`; kipy `run_action` for invocation.
- **AT-SPI unknown**: wxAccessible is MSW-only ([wx docs](https://docs.wxwidgets.org/latest/classwx_accessible.html)); GTK-native menus may surface with geometry "for free", AUI toolbars/canvas likely opaque. **This is the one accessibility verdict resolvable on this machine** — pending live probe.
- **In-repo MCP fork (audit)**: wraps file parsing + one narrow kicad-cli path only; **IPC not used anywhere** (`upstream/kicad_mcp/server.py:129`); the sole UI-touching upstream tool (`open_project`) and all geometry-touching tools are dead by omission (`solus/registration.py` TrimmingRegistrar, 5-of-16 exposure pinned by `tests/test_overlay_tool_trimming.py`). A TU-01 IPC/UI probe is **net-new surface**; reuse from the fork = `bin/launch` env-scrub posture, `cli_detect.py` degraded-reason pattern, `confinement.py` path law, `allowlist.yaml` shape, `tests/fixtures/solus_sample/` fixtures. Vendored `upstream/docs/*.md` (11 guides) are TU-02 ingestion material.
- **Customer-content trap**: IPC `get_open_documents`/`get_project` return customer paths/names; live action harvesting includes PCM plugin actions; `user.hotkeys` reflects remaps. Harvest from source tags / versioned docs / clean installs only.

### 2.6 Altium Designer

- **Server:Process addressing is the automation spine**: every command addressed as `Server:Process` with string parameters, invoked via RunProcess / `ICommandLauncher.LaunchCommand` / `X2.EXE -R…` CLI. Zero geometry; exactly the logical layer the KB wants. Dialog-opening processes run modal VCL dialogs *not* addressable through the API. ([scripting](https://www.altium.com/documentation/altium-designer/scripting), [PCB:Zoom example](https://www.altium.com/documentation/altium-designer/pcb-cmd-zoomzoom-ad?version=21))
- **Four enumeration channels, all logical**: vendor per-command doc pages (`?version=` scoped — best KB source); DXP » Run Process dialog; on-disk `.ins` process-table manifests (statically parseable, offline); programmatic `IClient`/`IServerProcess`/`IGUIManager` (hotkeys, panel metadata, launcher captions). ([IClient](https://www.altium.com/documentation/altium-dxp-developer/iclient-interface), [System API](https://www.altium.com/documentation/altium-dxp-developer/system-api), [TR0135 (2006)](https://gotomation.info/wp-content/uploads/2020/03/Scripting-system-reference-TR0135-System-Reference.pdf))
- **Geometry**: the API never returns coordinates — `IGUIManager.ResizePanel` is write-only sizing, `IServerPanelInfo` is metadata-only. Escape hatch: raw HWNDs (`GetRealMainWindowHandle`, `IExternalForm.Handle`) → Win32 `GetWindowRect` for windowed containers; custom-drawn contents (canvas, dialog controls) have no per-control handles. Whether later releases added rect getters is unknown (full method-level reference verified is TR0135 v1.4, 2006). Floating-panel/multi-monitor behavior untested.
- **No official external API** — corroborated by community `altium-mcp` bridging via CLI + JSON file polling ([deepwiki](https://deepwiki.com/coffeenmusic/altium-mcp/2.1-altiummcp-server-implementation)); absence well-corroborated but not vendor-stated.
- **UIA unknown**: Delphi/VCL app, no vendor a11y statement; community automation uses AutoHotkey keystrokes rather than UIA elements ([AHK addons](https://github.com/Altium-Designer-addons/scripts-libraries/blob/master/AutoHotKey/README.md)) — weakly suggestive of poor exposure, inference not evidence.
- **Customer-content trap**: live install blends vendor servers, marketplace extensions (own `.ins`), and user script bindings (`ScriptingSystem:RunScript` params embed user file paths); menus/toolbars per-user customizable. Partition by origin: stock install dir = vendor; extensions dir = third-party; script bindings/customization = customer.

## 3. Gaps → Fallback Ladder

Ladder: **TU-01** (programmatic surface) → **TU-02** (docs ingestion) → **TU-03** (visual/screenshot grounding). Each geometry or enumeration gap maps to its fallback:

| Gap | Tool | Fallback |
|---|---|---|
| No API for built-in command set; help-site menus/shortcuts only | Onshape | **TU-02**: scrape help-site menu/toolbar/shortcut pages + FeatureScript std/FsDoc (vendor, versioned) |
| WebGL viewport — no DOM geometry for parts/sketch entities/manipulators | Onshape | **TU-03**: visual grounding is the *only* option inside the canvas |
| DOM selector fragility (~3-week releases, no pinning) | Onshape | Not a ladder step — operational: date-scoped, monitored, centrally-updatable selectors; **TU-03** as break-glass when selectors die |
| No rects for toolbar/tabs/panels chrome (structure-only API) | Fusion | **TU-03**: visual localization of chrome, seeded by the logical tree (command name/icon/order from `commandDefinitions` + `ToolbarControl.index` narrows the visual search) |
| Qt accessibility exposure of custom toolbar untested | Fusion | Empirical probe (off-machine, Win/macOS install) before any KB claim; until then **TU-03** |
| Rolling doc set, no per-version archive | Fusion | **TU-02** ingestion must snapshot with capture date + build number |
| `GetButtonPosition` semantics (coord space, ribbon coverage) undocumented | SolidWorks | Off-machine empirical probe; interim **TU-03** verification of returned coordinates |
| No rect API for Task Pane / PMP / FeatureManager; native-tab button enumeration missing | SolidWorks | Win32 child-window enumeration (fragile, locale-dependent) → verify visually via **TU-03**; native-tab *contents* from **TU-02** per-year docs |
| UIA coverage of CommandManager unknown | SolidWorks | Off-machine Inspect.exe/FlaUI probe; **TU-03** until proven |
| No documented ribbon rect API; WPF-walk undocumented | AutoCAD | UIA probe (off-machine) is the plausible channel; fallback **TU-03** seeded by CUIx logical structure (tab/panel/item names + icons make visual matching near-deterministic) |
| Canvas overlay anchoring | AutoCAD | Covered — `Editor.PointToScreen` is documented; no fallback needed for drawing entities |
| SWIG geometry channel dies at 11.0; GAL canvas transform unverified | KiCad | **TU-03** long-term for chrome+canvas; short-term probe SWIG on 9/10 with hard expiry tag; canvas-transform question resolvable in the pending **on-machine probe** |
| AT-SPI exposure unknown (wxAccessible MSW-only) | KiCad | **On-machine probe pending** — resolvable here, do it before writing the fallback |
| IPC has zero UI geometry (by design) | KiCad | Permanent: **TU-02** (versioned manuals) for structure + **TU-03** for pixels |
| No rect getters in API; custom-drawn contents opaque to HWND bridge | Altium | Coarse Win32 rects for panels/windows + **TU-03** for per-control geometry; **TU-02** (`?version=` command docs + `.ins` parsing) for everything logical |
| UIA quality vs VCL unknown | Altium | Off-machine Inspect.exe/Accessibility-Insights probe; assume **TU-03** until evidence |

**Pattern worth stating**: for all four Windows desktop tools, logical structure (TU-01/TU-02) is rich enough to *seed* TU-03 — visual grounding never searches blind; it confirms the location of a command it already knows by name, icon, parent panel, and ordinal position.

## 4. Implications for KB Catalog Seeds

**Mechanically enumerable — no docs parsing required for the command catalog:**

| Tool | Mechanism | Caveat |
|---|---|---|
| **AutoCAD** | Unzip shipped `acad.cuix` — full UI+command+macro catalog, **offline, no install run needed** | Whitelist to stock CUIx; schema vendor-unwarranted; union with Command Reference for demand-loaded commands |
| **SolidWorks** | Scrape per-year `swCommands_e` help pages (3000+ IDs, **no install needed**; browser UA + `__NEXT_DATA__` extraction) | Enum names ≠ UI labels (needs curation); numeric stability across years unverified — harvest per-year and diff |
| **KiCad** | GPL source at a git tag → exact per-version TOOL_ACTION catalog; + `kicad-cli --help`; **fully offline, fully vendor-pure** | The cleanest seed of the six; `run_action` names drift (unstable) |
| **Fusion** | One-time add-in run: `commandDefinitions` + workspace tree dump (vendor sample proves the pattern) | Requires a live install (off-machine); must run add-in-free; date+build stamp mandatory |
| **Altium** | Parse stock `.ins` files from a clean install dir (**offline once files obtained**); or scrape `?version=`-scoped vendor command pages | Partition install dir vs extensions vs user profile; doc scrape is the version-tagged option |

**Docs parsing required (no mechanical command enumeration):**

| Tool | Why | Seed source |
|---|---|---|
| **Onshape** | No API lists built-in commands — flatly | Help-site scrape (menus/toolbars/shortcuts) + FeatureScript std/FsDoc for feature semantics; extension-location vocabulary from app-dev docs |

**Universal ingestion laws (every tool exhibited the same trap class):**
1. **Customer-content firewall** — the Onshape-featurespecs trap recurs everywhere: Fusion add-in command defs, SolidWorks per-document tabs/add-in events, AutoCAD partial CUIx, KiCad PCM plugins/`user.hotkeys`/IPC document specifiers, Altium extension `.ins`/script bindings. Rule: harvest only from vendor docs, source tags, shipped stock files, or clean vanilla installs; tag provenance on every entry; never ingest window/document titles or file paths.
2. **Version tagging is non-optional and per-tool shaped**: exact version floors (SolidWorks "Availability" lines, KiCad doc-URL series, Altium `?version=`) vs capture-date-only (Fusion build stream, Onshape UI). Two-regime tools (Onshape: versioned API / unversionable UI) need split scoping per fact.
3. **Geometry facts are not KB facts** for Onshape DOM and anything accessibility-derived until probed — geometry lives in the runtime/overlay layer with monitoring and expiry, not in the durable catalog. The durable catalog holds logical structure; the two exceptions where documented geometry APIs *are* KB-worthy: SolidWorks (Frame*/GetButtonPosition/HWND bridge, with version floors) and Fusion (Palette/Viewport, date-stamped).
